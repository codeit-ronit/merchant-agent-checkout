What this is

A control plane that sits between an agent and its money-moving tools

Agents are increasingly pointed at APIs that move money. The standard guardrail is a sentence in a system prompt — a request to the model, not a property of the system. SENTINEL intercepts every tool call at the protocol boundary, classifies it, redacts PII, evaluates it against declarative policy, and allows, denies, or escalates it to a human — before it executes.

It does four things

  1. Enforces policy at the tool-call boundary, not in the prompt.
  2. Redacts PII before it reaches the model and quarantines untrusted text.
  3. Writes a tamper-evident, hash-chained audit trail of every decision.
  4. Proves it works via a deterministic eval harness and a red-team A/B suite.

The decision vocabulary

Every tool call ends in one of these states — legible at a glance, and distinguishable without colour via its glyph:

✓ ALLOW ✕ DENY ▲ REQUIRE_APPROVAL ⏱ AWAITING

Every decision carries an enumerated reason code and a plain sentence an operator can act on. A block without a reason is a bug.

The one claim everything serves: a completely different MCP client pointed at the proxy is subject to the same policy. That is not true of any prompt. Prompt guardrails are requests to the model; proxy guardrails are properties of the system — and only the second kind can be tested, audited, or trusted with money.
01 · Why it exists

An agent with write access is a security surface, not a feature

A no-code builder is about to let non-engineers point LLM agents at APIs that move money. Those agents read PANs, bank statements, and settlement records, and they ingest attacker-controlled text by design: support tickets, chargeback evidence, uploaded statements, merchant notes. Four concrete failures follow:

1 · Guardrails live in the prompt

"Never refund without confirming" is a request, not a constraint. It degrades under long context and adversarial input, cannot be unit tested, and produces no artefact when it works or fails.

2 · Attacker text reaches the model with tools attached

A chargeback bundle, a bank-statement text layer, a support ticket — any can carry an instruction. The agent has no principled way to tell "data I was asked to analyse" from "instructions I was given."

3 · No record survives scrutiny

When an agent does something wrong with money: what did it do, in what order, on whose authority, with what inputs — and could the log have been altered? Standard logging answers none of these well.

4 · No way to know if a change made things worse

Prompt tweaks, model upgrades, and new tools ship on vibes. "It seemed fine when I tried it" is the state of the art for agents touching financial APIs.

02 · The central decision

Enforcement in a process the model does not control

There are three places to put a guardrail. SENTINEL implements the second and third, and treats the first as documentation.

System prompt◌ ADVISORY
The model may comply. Adversarial input, context pressure, and model updates all erode it. Untestable.
↓
In-loop guard · layer 2 — the experienceSTRONG
Runs in our process. Gives structured, model-readable denials and rich context (stated reasoning, step number, run state). Not the guarantee — it shares a process with attacker text.
↓
SENTINEL MCP proxy · layer 1 — THE GUARANTEESTRONGEST
Protocol-level. Cannot be bypassed. Fails closed. Enforces regardless of which agent, framework, or model — survives the agent being replaced entirely. classify → redact → evaluate → allow/deny/escalate → idempotency → forward.

Both layers call the same pure policy engine with the same context builder. If they ever disagree, the proxy wins and the disagreement is logged as a LAYER_DISAGREEMENT P0 incident — because it means one of them has a bug. The model runtime is provider-agnostic by design: an in-house ~200-line loop over a thin abstraction, demonstrated across two providers, so the enforcement result can be shown to hold regardless of model.

Components, each with exactly one job

MCP Proxy

Speaks MCP both sides. Discovers & filters the tool manifest. Runs the decision pipeline.

Policy Engine

A pure function. No I/O, no clock, no randomness. Exhaustively testable.

Redaction Service

PII → stable tokens inbound; rehydrate only where a tool legitimately needs it.

Quarantine

Untrusted text wrapped in a per-run nonce delimiter; permissions narrow.

Audit Ledger

Append-only, SHA-256 hash-chained, gapless sequence, with a verifier.

Approval Store

Single-use, argument-bound, expiring escalations. Re-validated on resume.

Provider Abstraction

Normalised tool calling, failover, rate-limit governor, cassette record/replay.

Idempotency Guard

A retried refund is not a second refund. Deterministic key per mutating call.

Fixture Server

A faithful, deterministic double of the upstream. The red-team runs here only.

03 · One tool call, end to end

The request lifecycle

The sequence to implement and the sequence to explain. Every one of steps 04–12 can fail closed independently.

  1. Agent loop sends messages + tool manifest via the provider abstraction. Cassette hit → replay; miss → call & record. Rate limit → back off, fail over.
  2. Provider returns a tool call. Loop builds a DecisionContext and runs the in-loop guard. A DENY short-circuits with a structured, model-readable denial.
  3. Call reaches the SENTINEL MCP proxy over the MCP protocol.
  4. Classifier resolves the risk class. UNKNOWN → DENY, fail closed.
  5. Argument validation against the declared schema. Malformed → DENY. Never guess a money-moving call's arguments.
  6. Redaction rehydrates placeholder tokens. A token never issued → DENY + flag suspected exfiltration.
  7. Policy engine evaluates (authoritative). ALLOW → continue · DENY → block+audit · ESCALATE → create approval, suspend, await human.
  8. Idempotency guard checks the key. Seen → return the stored result, no execution.
  9. Forward to upstream (fixture or live).
  10. Result returns. Scan for PII → redact → replace with stable tokens.
  11. Classify field provenance. Wrap UNTRUSTED text in the nonce-delimited quarantine.
  12. Write the audit entry: decision, reason code, matched rule, redacted args, latency, tokens, provider, model, cost, chain hash.
  13. Return to the model. The loop appends the result and iterates.
  14. Trace event streamed to the UI and persisted for eval replay.
04 · The pure decision core

Policy is a file a non-engineer can read and a test can assert on

The engine is evaluate(policy_set, decision_context) → PolicyDecision — a pure function: no I/O, no clock, no network, no randomness. Time, spend, counts, and approval status are all injected via the context. That purity buys exhaustive unit testing, property-based testing, and replay (apply a candidate policy to a historical run and see exactly which decisions change).

Evaluation semantics

  • All rules evaluate — no short-circuit — so every match is recorded.
  • Most-restrictive-wins: DENY > REQUIRE_APPROVAL > ALLOW, unconditionally.
  • No permitting rule → DENY DENY_FAIL_CLOSED.
  • Any exception → DENY DENY_POLICY_EVALUATION_ERROR + abort the run.
  • Precedence is by restrictiveness, never file order.

A closed set of rule types — not a DSL

An expressive DSL is a new attack surface and an untestable space. The two most interesting:

  • provenance_guard — untrusted text in context → the permission set actually shrinks. The structural answer to injection.
  • counterparty_novelty — a payout to an unseen destination is the highest-risk action; it always escalates.
A system invariant, not a config default: no policy file — however maliciously written — can auto-allow a MONEY_MOVEMENT tool without approval. This is enforced above the policy layer, and a test proves a hand-crafted file cannot configure it away.
05 · The model never needs the digits

Redaction and the trust quarantine

For almost every task these agents do, PII is used as an identity token, not a value. A reconciliation agent needs to know account ACCT_a17f appears in both records — not the digits. So we replace PII with a stable, greppable token before it ever reaches the model, and keep the token→value map in a store the model cannot address.

The invariant we test relentlessly

No real PII value appears in any prompt, trace event, audit entry, log, API response, or file on disk outside the token store. Implemented as a parametrised test that seeds the pipeline with known synthetic PII and greps every output surface. The highest-value test in the repo.

Two mechanisms against injection — and only the second holds

1 · Nonce-delimited quarantine mitigation

Untrusted text is wrapped by the proxy in a delimiter carrying a per-run cryptographic nonce. A fixed delimiter is trivially defeated by anyone who reads the source; a random nonce cannot be guessed. Reduces attack success — does not eliminate it.

2 · Permission narrowing the guarantee

When untrusted content enters a run, the agent's permissions shrink for the rest of it: irreversible writes downgrade to escalation, reads tighten to entities already in scope. We do not need to know whether the injection worked — we assume it might have and reduce what a compromised agent can do.

06 · The signature element

A record that visibly breaks when tampered

Each ledger entry contains the SHA-256 hash of the previous entry; its own hash covers its canonical serialisation including that previous hash. Alter any entry and every entry after it fails verification. Try it — tamper with a block and run the verifier:

chain intact — 6 entries
Honest by design — tamper-EVIDENT, not tamper-PROOF. Anyone who can write to the database can recompute the whole chain from any point and it will verify cleanly. Real tamper-resistance needs an external anchor (an RFC 6962-style transparency log) or write-once storage — neither is implemented, and that is stated plainly in LIMITATIONS.md.

08 · The rarest skill in the space

Making "did this get better?" a number, with no API key

Everything runs against fixtures and committed cassettes — recorded model interactions keyed by a content hash of everything that could change the response. A reviewer clones the repo and reproduces the exact eval numbers with no credentials. A cassette miss in replay mode is a hard failure, never a silent fall-through to the network.

The red-team A/B — the evidence

Every injection payload runs under identical conditions with guardrails off and on. Grading is rule-based and deterministic, derived from the trace and audit log — never a model judging outputs. Three numbers, all reported honestly:

Attack success · OFF100%no control plane — 12 L4 + 1 L3
Attack success · ON0%0 L4, 0 L3 · 12/13 L1 (harmless)
False-positive rate0%legitimate work never blocked
We did not solve prompt injection — nobody has. Quarantine is a mitigation; permission narrowing is the guarantee. With guardrails on, 12 of 13 attacks still altered behaviour (L1) — and it did not matter: L3 (exfiltration) and L4 (unauthorised money movement) were zero. The goal is to make being fooled harmless, not impossible.

Multi-model finding

Strong model: 100% task success, 0 malformed calls. Weak model: 81%, 13 malformed calls, lower hard-case accuracy. Both: 0 unauthorised executions, 0 PII leaks, 0 policy errors. Accuracy varied; enforcement did not — because it lives in the proxy, not the model.

Ablation — which control did the work?

Turning one control off at a time (guardrails-on):

Policy prevents L4; redaction prevents L3; the nonce quarantine's marginal effect was negligible — less than intuition suggests, reported because it contradicts the design assumption (ADR-021).

09 · Every choice, with its cost named

Key decisions

Recorded at the time in DECISIONS.md. An ADR without a named trade-off is marketing. A selection:

ADR-000 Offline-first, credential-free demonstration
Fixture upstream + committed cassettes + a deterministic scripted provider, with real provider adapters that activate only when a key is present. Trade-off: cassettes must be authored and kept fresh; an incomplete cassette key would produce stale replays that look like passing tests.
ADR-001 Enforcement placement: proxy + in-loop, prompt as docs
The proxy is the guarantee; the in-loop guard is the experience. Both call the same pure engine. Trade-off: two enforcement paths to keep in sync, guarded by a permanent layer-agreement test.
ADR-002a Providers: Groq primary, Gemini fallback
Both OpenAI-compatible, so one adapter shape covers both and the loop never branches on provider. Verified live 2026-08-21. Trade-off: Gemini's free tier trains on inputs — mitigated by synthetic-only data, stated in the README.
ADR-006 Money is integer minor units, enforced at serialisation
Razorpay uses integer paise (₹299 = 29900). The canonical serialiser raises on any float. Trade-off: callers convert at the edge; the engine never divides.
ADR-010 Canonical JSON (RFC 8785-inspired) + SHA-256
Stricter than the RFC: floats forbidden, large ints carried as strings. Trade-off: tamper-evident, not tamper-proof — needs an external anchor for real resistance.
ADR-011 Our own idempotency guard
Native Razorpay idempotency is payout-only, and the MCP server exposes no payout tool — so no reachable money-moving tool has native coverage. We supply a deterministic key per mutating call. Trade-off: per-run guard, not an upstream guarantee.
ADR-018 Rule-based red-team grading; make being fooled harmless
Grading from trace + audit, never a model judge. Corpus informed by OWASP LLM01, Spotlighting, CaMeL, AgentDojo, InjecAgent. Trade-off: rule-based grading can miss subtle behaviour changes; we accept coarser but trustworthy grades.
10 · Verified live, not from memory

What the research found

Free-tier catalogues and the upstream tool inventory change monthly, so all of this was fetched from live sources on 2026-08-21 and dated in DECISIONS.md.

Razorpay MCP surface (~45 tools)

Money-movement set: capture_payment, initiate_payment, submit_otp, create_refund, create_instant_settlement. Notably no create-payout tool and no dispute tools exist upstream.

Amounts are integer paise. Pagination is offset-based (count/skip, default 10, max 100). The server does not enforce test-mode — so our proxy must.

Indian PII formats + safe generation

Checksummed types (Aadhaar/Verhoeff, GSTIN/Luhn-36, card/Luhn-10) get a deliberately wrong check digit; checksum-free types (IFSC, VPA, UTR, mobile, account) use structural reservation (ZZZZ bank code, @invalid handle, impossible Julian day). No synthetic value can collide with a real one.

Canonical form + hash

RFC 8785 (JCS) — with its number-handling landmine avoided by forbidding floats and carrying large ints as strings. SHA-256 for the chain (RFC 6962 family). Tamper-evidence reduces to collision resistance.

Injection taxonomy

OWASP LLM01 (direct/indirect/multimodal); Spotlighting/datamarking measured but incomplete under adaptive attack; the CaMeL framing — separate control from data, least privilege. Benchmarks cited: AgentDojo (has a Banking domain), InjecAgent.

12 · No credentials required

How to run it

The demo, tests, evals, and red-team all run offline in fixture mode with cassette replay.

$ make install   # venv + deps
$ make test   # tiers 1–3, fast, no model
$ make demo-cli   # a money-movement denial with a plain reason
$ make verify-audit   # walk the hash chain
$ make eval      # golden set + regression gates
$ make redteam  # paired A/B, fixture-only
