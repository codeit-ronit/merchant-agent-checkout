# 09 — Interface

## 1. What we are solving

**Make the invisible visible.** An agent buying something is, in raw form, a text log. The interesting part — the cart forming, the mandate draining, the commit gate deciding — happens where nobody can see it.

Two audiences with genuinely different jobs:

- **The buyer** wants to state a need and see it handled, with enough visibility to trust it.
- **The merchant** wants to know they are sellable, see what agents bought, and control the rules.

## 2. The signature: the split view

The one thing this interface is remembered by.

**Left: the conversation.** A person states a constraint. The agent responds. Human-legible, calm.

**Right: the machinery, live.** The cart assembling line by line with server-computed totals. The mandate balance draining. Each policy decision as it fires. The commit gate's re-price diff. The Razorpay order id appearing at the end.

Why this is the right signature: it embodies the entire thesis in one screen. A chat window alone proves nothing — anyone can fake a conversation. The split view shows that behind every sentence there is a bounded, priced, audited action, and that the two are locked together in real time.

**The moment to design for:** the agent says "adding paneer tikka" on the left, and simultaneously on the right a line item appears, the total recomputes, and the mandate bar shrinks. That synchrony is the demo.

## 3. Buyer surface

Beyond the split view:

- **Mandate creation** — the one human step. Amount, merchant, expiry. Should feel like setting aside money, not filling a form. This is the "consent moves upstream" moment made tangible.
- **Receipt** — what was bought, what it cost, which mandate authorised it, which rule permitted it, the Razorpay order id, and the audit reference. Upsells marked as upsells with the rule that offered them.
- **Failure states** — a decline, a re-price, an out-of-stock. Each explains what happened, what state things are in, and what to do next. These are the screens most projects neglect and the ones that carry the "handled gracefully" requirement.

## 4. Merchant console

- **Catalog** — items, prices, availability, and **which fields are trusted versus untrusted**. Showing the merchant that their descriptions are treated as untrusted text is honest and unusual.
- **Onboarding** — the three paths from `03-CATALOG.md`, with the step count and elapsed time visible. If becoming sellable is genuinely fast, show it.
- **Mandates** — active, remaining balance, expiry, with a revoke control that works instantly.
- **Orders** — what agents bought, with the full trace behind each.
- **Upsell rules** — author, cap, and see acceptance rates.
- **Audit** — carried over from SENTINEL, with the chain verification button.

## 5. Real versus modelled — surfaced, not buried

Catalog, cart, and mandate are modelled. Razorpay calls are real.

**Show this in the interface.** A persistent, quiet indicator distinguishing modelled components from live API calls, and in the run trace, each call marked as one or the other.

Two reasons. It is honest, and this repository has already built the habit — the tool reconciliation view reports fixture extensions as fixture-only rather than pretending. And it is *more* impressive: a system that says out loud "here is the line between what I built and what is real" reads as confident. A system that blurs it invites the question.

## 6. Design direction

The subject is **an agent spending someone's money under a limit they set.** Not a chatbot, not a dashboard. The vernacular is authorisation, drawdown, commitment, receipt — the language of a ledger, not an app.

**Deliberate choices required. Do not default.**

- **Palette:** 4–6 named values chosen for this brief. The information colour must carry is *state*: authorised, spending, committed, blocked, exhausted. All must be distinguishable without colour — this is financial software and colour-blind users exist.
- **Typography:** a display face and a body face, plus a genuine monospace for amounts, ids, and hashes. **Amounts must be tabular-figure aligned.** Misaligned money in a financial interface is a correctness signal, not an aesthetic one.
- **Motion, used once and precisely:** the mandate drawdown. It is the only element where a value moves continuously and where the motion carries meaning — money being consumed. Everywhere else, restraint. Scattered animation is the strongest tell of AI-generated design.
- **Structure:** the purchase is a genuine sequence — constraint, cart, commit, payment, receipt — so sequential structural devices encode something true here. Use them there and nowhere they do not belong.

**Calibrate away from defaults.** Current AI-generated design clusters around three looks: warm cream with high-contrast serif and terracotta accent; near-black with one acid accent; broadsheet with hairline rules and zero radius. All legitimate for some brief; none should be chosen here by default. Spend the freedom on something specific to money moving under a limit.

**Spend boldness in one place.** The split view is the bold element. Everything around it stays quiet.

## 7. Copy

Write from the user's side of the screen. Name things by what people control, never by how the system is built.

- "₹2,000 set aside for Fresh Basket" — not "mandate created"
- "Blocked: this would take you ₹340 over your limit" — not "DENY_MANDATE_EXHAUSTED"
- "The price changed while we were shopping. Paneer tikka is now ₹240, up from ₹200. Total is ₹840." — not "reprice divergence detected"

Active voice. An action keeps its name through the whole flow: the button that says "Set aside" produces a state that says "Set aside." Errors explain what happened and what to do next; they never apologise and are never vague. Empty states invite action.

## 8. Quality floor

Responsive to mobile. Visible keyboard focus. Reduced motion respected. Working empty and error states for every view — specified before either is built.

## 9. Acceptance criteria

- [ ] Split view: conversation and machinery synchronised live
- [ ] Cart, totals, and mandate drawdown update in real time as the agent works
- [ ] Every policy decision visible with its plain-language reason
- [ ] Re-price diff rendered itemised and legible
- [ ] Mandate creation feels like setting aside money, not filling a form
- [ ] Revoke works instantly and visibly
- [ ] Real versus modelled surfaced persistently, not buried
- [ ] Receipt names the mandate, the permitting rule, the order id, and any upsell
- [ ] Failure states explain state and next step
- [ ] Amounts tabular-aligned; states distinguishable without colour
- [ ] Responsive, keyboard navigable, reduced motion respected
- [ ] Every view has designed empty and error states
